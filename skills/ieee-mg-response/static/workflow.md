# Response 撰写工作流

> **v0.4.0**：融入 grill-me 强制询问机制、三步清单输出流程、禁止直接写 tex 规则、
> 多轮迭代工作流、Gate 同步检查、交叉验证流程。
> 基于 3 篇论文 Response（TWC×2 + TGCN×1，73 条评审意见）蒸馏。

## ⚠ 核心前置规则

**禁止直接写入 tex 文件**。本技能的工作流产出是 `.md` 文档，不是 `.tex` 文件。用户确认清单后，再将清单内容转化为 tex 格式。

---

## 完整 Response 撰写流程

### Phase 0：输入完整性检查

收到用户请求后，**首先检查输入完整性**：

| 场景 | 检查项 | 操作 |
|------|--------|------|
| 用户提供了完整返修邮件 | 包含 Editor 意见 + 所有 Reviewer 意见 + 编号完整 | ✅ 进入 Phase 1 |
| 用户提供了部分返修意见 | 缺少 Editor 或某个 Reviewer | ❓ 询问：**"您提供的意见似乎不完整，缺少 [具体缺失部分]。请问是否有完整的返修邮件？"** |
| 用户仅描述了任务 | 未提供任何审稿意见原文 | ❓ 询问：**"请提供审稿意见原文（完整的返修邮件或意见截图/文本）。没有原文无法生成有针对性的回复。"** |
| 用户提供了 tex 文件 | 可从 tex 中提取意见 | ✅ 从 tex 中提取 Comment 内容，进入 Phase 1 |

**不可跳过此步。不完整的输入会导致生成无效回复。**

---

### Phase 1：意见提取与编号

从用户提供的材料中提取所有评审意见。

**输出目录**：在论文原文所在目录下创建 `output/` 子目录，所有产出文件存放于此：

```
[论文目录]/
├── [论文原文].tex
├── [返修邮件].md
└── output/                          ← 所有产出存放于此
    ├── comments_list.md             ← Phase 1 产出
    ├── comments_translated.md       ← Phase 1 产出
    ├── response_plan.md             ← Phase 3 产出
    └── Response_[稿件ID].tex        ← Phase 5 产出
```

按以下格式整理：

**输出文件 1**：`comments_list.md`（返修意见清单）

```markdown
# 返修意见清单

## Editor
| 编号 | 来源 | 评论摘要 |
|------|------|----------|
| E-1 | Editor | [简要描述] |
| E-2 | Editor | [简要描述] |

## Reviewer 1
| 编号 | 来源 | 评论摘要 |
|------|------|----------|
| R1-1 | Reviewer 1 | [简要描述] |
| R1-2 | Reviewer 1 | [简要描述] |

## Reviewer 2
...

## Reviewer N
...

---
**统计**：Editor X 条 + Reviewer 1 X 条 + ... = 共 X 条
```

**输出文件 2**：`comments_translated.md`（评论翻译版，中英对照）

```markdown
# 返修意见翻译版（中英对照）

## Editor

### E-1
**原文**：[审稿人英文原话，逐字引用]

**翻译**：[中文翻译，保留技术术语]

---

### E-2
...

## Reviewer 1
...
```

**注意事项**：
- 原文必须逐字引用，不可改写或缩写
- 翻译需准确传达技术含义，保留专业术语
- 如审稿人意见中包含编号子项（(a), (b), (i), (ii)），保留原始编号

### Phase 2：逐条分类与询问 + 评估方案生成

> 这是本技能最核心的步骤。**每条修改型意见必须经过询问确认后才可撰写。**

#### 2.1 自动分类与评估

先通读论文原文和所有返修意见，对所有意见进行自动分类，并生成评估维度：

| 维度 | 说明 |
|------|------|
| **紧迫度** | 🔴 缺失则拒稿 / 🟡 改善质量 / 🟢 可选优化 |
| **复杂度** | 高（需推导/仿真/新图）/ 中（文字修改）/ 低（格式修正） |
| **破坏度** | 高（需重推公式）/ 中（需补充推导）/ 低（仅措辞） |
| **推荐策略** | 接受 / 拒绝 / 部分接受（含子方案 A/B/C） |

#### 2.2 第一轮：输出所有问题（Q1-QN），然后停止

**⚠ 这是两轮交互模式的「第一轮」。输出完所有问题后，AI 必须停止，等待用户回复。**

AI 将所有需要用户确认的点整理为 Q1-QN，一次性输出。每条包含：
- 评论编号 + 摘要
- AI 判断的类型
- 审稿人原文（简要）
- AI 推荐的方案（1-3 个候选）
- 需要用户确认的选择

**输出格式**：

```
📋 分类结果概览

| 编号 | 类型 | 紧迫度 | AI 推荐 |
|------|------|:------:|----------|
| E-1  | 澄清型 | — | 确认提交格式 |
| R1-1 | 修改型 | 🔴 | 接受，新增 Motivation 子节 |
| R1-2 | 部分接受 | 🟡 | 接受量化论证，拒绝新增 CSI 研究 |
...

---

❓ **Q1 — R1-1 [新增 Motivation 子节]**
类型：修改型 | 紧迫度：🔴
审稿人要求：在 Section I 新增 "Motivation and Novelty" 子节，与 [43]/[45] 对比
AI 推荐：接受。在 Section I-A 扩展 "Motivation and Novelty" 第一段，增加并排对比

➡️ 推荐：采纳
[ ] 采纳
[ ] 拒绝（请说明理由）
[ ] 部分采纳（请说明）
[ ] 我有自己的方案

---

❓ **Q2 — R1-2 [cross-region 论证]**
类型：部分接受 | 紧迫度：🟡
审稿人要求：量化 cross-region 简化合理性 + 考虑 imperfect CSI
AI 推荐方案 A：接受量化论证部分，在 Section II 补充路径损耗差距说明；拒绝新增 CSI 研究（超出范围）
AI 推荐方案 B：全部接受，新增简短 imperfect CSI 分析

➡️ 推荐：方案 A
[ ] 方案 A
[ ] 方案 B
[ ] 我有自己的方案

---

[... 所有 Q1-QN ...]

---

⚠️ 请将以上 Q1-QN 全部回复后发送，我将根据您的回答继续执行后续流程。
```

#### 2.3 等待用户回复

**在用户回复所有 Q1-QN 之前，AI 绝对不可继续执行 Phase 3 或后续流程。** 这是铁律。

#### 2.4 第二轮：读取用户回答，继续执行

用户将 Q1-QN 的回复一次性发送后，AI 执行：

1. **解析回答**：读取用户对 Q1-QN 每条的选择和补充说明
2. **确认策略**：将用户回答转化为确定的修改策略
3. **进入 Phase 3**：基于确认的策略生成 response_plan.md

#### 2.5 澄清型和拒绝型的特殊处理

- **澄清型**：AI 可直接给出澄清方案（因为无需修改正文），但仍需用户确认
- **拒绝型**：AI 给出拒绝理由和引用支撑，用户确认拒绝策略
- **修改型**：**必须询问**，不可跳过

---

### Phase 4：用户确认方案

向用户展示 `response_plan.md`，询问：

```
以上回复方案是否满意？请确认以下事项：
1. 每条回复的内容是否准确反映了您的意图？
2. 修改位置和蓝色高亮文本是否正确？
3. 引用文献是否完整？
4. 语气和措辞是否合适？
```

用户确认后进入 Phase 5。

> **多轮迭代模式**（语料实测）：实际项目中，修改方案经历了 v3.0→v5.1 共 6 个版本的迭代优化。每轮使用 4 个并行子代理分别从不同角度审查：
> - **技术正确性审查**：公式/推导/数值是否正确
> - **对抗性审查**：假设是否合理、论证是否充分
> - **一致性审查**：模板/翻译/方案/正文是否同步
> - **完整性审查**：是否遗漏任何评论
>
> **终止条件**：当所有子代理审查发现数连续 2 轮为 0（或用户明确表示满意）时终止迭代。默认最多 4 轮。

### Phase 5：生成 tex 文档

将确认的 `response_plan.md` 转化为完整 `.tex` 文件。

#### 两种模式

**模式 A：完整生成**（推荐用于评论数 ≤ 10 条时）
- AI 一次性生成完整 .tex 文件
- 直接参照 `section-latex-template.md` 的模板替换内容

**模式 B：分段生成**（推荐用于评论数 > 10 条时）
- 按 Reviewer 分段生成，每次生成一个 Reviewer 段落
- 用户确认每段后再生成下一段，避免上下文溢出

#### 分步组装流程

1. **Preamble**：参照 `section-latex-format.md` 的标准 preamble，加载必要包和自定义命令（`\mySep`、`\RevisedExcerpt`）
2. **封面页**：参照 `section-latex-template.md` 的 Cover Letter 格式
3. **Editor 段落**：编号逐点格式（1), 2), 3)...），详见 `section-editor-response.md`
4. **Reviewer 段落**（逐个处理，每个 `\clearpage` 分隔）：
   - a) 居中 5 行段头块（期刊+ID+标题+回复标识+作者）
   - b) 段首致谢过渡段
   - c) 逐条 Comment/Response（用 `\mySep` 分隔，每条含 `\emph{}` 引用 + Response 正文 + `\begin{quote}` 蓝色摘录）
   - d) 段尾致谢 + 斜体作者签名
5. **交叉检查**：组装过程中同步确认 quote 块中的蓝色摘录与 `response_plan.md` 一致

> **注**：推荐直接以 `section-latex-template.md` 为起点，逐个替换占位符内容。

### Phase 6：Gate 同步检查（语料实测机制）

在生成 tex 之前，创建一份**同步检查清单**，防止复制未同步的模板内容：

```markdown
## Gate 同步检查清单

| 检查项 | grep 模式 | 状态 |
|--------|-----------|:----:|
| 所有 TODO/占位符已填充 | grep -n "TODO\|【TODO】\|\[待补\]\|\[待核\]" response_plan.md | ✅ |
| 方案版本号与最终版一致 | grep -n "存档\|draft\|草稿" response_plan.md | ✅ |
| 术语/符号一致性 | grep -n "EE \|BCPU\|ρ[^_]" main.tex response.tex | ✅ |
| 图表编号连续性 | grep -n "Fig\.\|TABLE" main.tex response.tex | ✅ |
| 参考文献编号匹配 | grep -n "\[R[0-9]\]" response.tex | ✅ |
```

> **注**：以上为通用模板，实际项目可按需增减检查项。核心原则是：模板/翻译/方案/正文四份文档必须同步，任何一处修改都要检查其他三处是否需要联动更新。

### Phase 7：交叉验证（正文 ↔ Response 一致性检查）

> 基于 sess_a425339e 对话中发现的真实问题蒸馏。

在生成 tex 之后、最终交付之前，**必须执行交叉验证**：

#### 7.1 提取与匹配
1. 提取正文（主 `.tex` 文件）中所有 `\textadd{...}` 块
2. 提取 Response 中所有 `\textcolor[rgb]{0.00,0.00,1.00}{...}` 蓝色摘录
3. 逐块匹配：正文每个修改块 ↔ Response 对应摘录

#### 7.2 一致性检查项

| 检查项 | 操作 | 严重性 |
|--------|------|:------:|
| **公式符号一致** | 检查变量名、上下标、希腊字母是否完全相同 | 🔴 |
| **术语缩写一致** | 正文用全称 "secrecy energy efficiency" 时，Response 不可缩写为 "EE" | 🔴 |
| **公式结构一致** | 公式的分子分母、等号左右必须完全匹配 | 🔴 |
| **图表编号转换** | 正文 `Fig.~\ref{label}` → Response `Fig.~N`（正确差异，非错误） | ✅ |
| **公式编号转换** | 正文 `\eqref{label}` → Response `(N)`（正确差异，非错误） | ✅ |
| **删除标记** | 正文注释掉的内容不应出现在 Response 中 | 🟡 |
| **脚注内容** | `\textadd{...footnote{...}}` 中的脚注内容必须在 Response 中完整展示 | 🔴 |

#### 7.3 常见陷阱（语料实测）

**陷阱 1：公式符号不匹配**
```
正文：EE = T_system^ς / P_total     （修改后版本）
Response：EE = T_system(R) / P_total  （未同步的旧版本）
→ 必须修改为：EE = T_system^ς / P_total
```

**陷阱 2：术语缩写不匹配**
```
正文：secrecy energy efficiency first increases...  （使用全称）
Response：the EE first increases...  （使用缩写）
→ 必须修改为：the secrecy energy efficiency first increases...
```

**陷阱 3：Response 中引用了正文不存在的修改**
```
Response：引用了某处蓝色修改，但正文对应位置无 \textadd{} 块
→ 需确认是否为纯澄清型回复（不应有蓝色摘录）
```

### Phase 8：自检清单

生成 tex 并完成交叉验证后，对照以下清单最终自检：

#### 内容完整性
- [ ] 每条评论是否都已回复？（编号无遗漏）
- [ ] 澄清型回复是否**未附**蓝色修改摘录？
- [ ] 修改型回复是否都标注了**具体位置**？
- [ ] 拒绝型回复是否提供了**充分理由**？
- [ ] 宽泛语法评论是否**逐项拆解**？
- [ ] 交叉验证是否通过？（正文修改 ↔ Response 摘录一致性）

#### 格式一致性
- [ ] 所有评论是否用 `\emph{}` 引用？
- [ ] 所有修改是否用 `\textcolor[rgb]{0.00,0.00,1.00}{}` 高亮？
- [ ] 位置标注是否精确到小节/段落/图表？
- [ ] 新图是否用 `\caption*{}` 而非 `\caption`？
- [ ] 分隔符 `\mySep` 是否一致？
- [ ] 是否零 `\cite{}` 命令（全部用纯文本引用）？
- [ ] Response 中是否使用字面编号（`Fig.~3`、`(10)`）而非 `\ref{}`/`\eqref{}`？
- [ ] 公式是否使用 `\begin{align}+\tag` 而非 `\begin{equation}`？

#### 语言质量
- [ ] 每条首句是否以感谢开头？
- [ ] 语气是否全程礼貌专业？
- [ ] 术语是否与 `ieee-mg-share/terminology.md` 一致？
- [ ] 术语缩写是否与正文一致？（正文用全称时 Response 不可缩写）

#### 交叉一致性（关键）
- [ ] 正文蓝色修改句与 Response 中蓝色摘录是否**逐字一致**？
- [ ] 公式符号（变量名、上下标、希腊字母）是否完全匹配？
- [ ] 新增图表编号是否连续？
- [ ] 新增参考文献 `[RN]` 是否已加入 `{\footnotesize{}}` 块？
- [ ] 脚注内容是否在 Response 中完整展示？
