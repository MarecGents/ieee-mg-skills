- **第三轮蒸馏（本轮核心）**：精细打磨——约束可执行性（量化判定标准）、思考深度（决策树分支/推理链）、判断边界（本地化落实）、灵活度（conf/mag 数值适配）、交叉一致性（去重/口径统一）、查漏补缺（语料实证错误/高频句式补录），产出 v1.3.0。

- `All Paper Title.md` —— 21 篇完整论文（仅含 Abstract / Introduction / Numerical Results / Conclusion 四部分；**不含 System Model 章节正文**，该章节优化只能基于组织句与动机中的间接线索，禁止编造语料数据）

### 现有技能体系（本轮优化对象）
- `ieee-mg-share`（共享层：style-profile / terminology / expression-bank / logic-connectors / section-architecture / common-errors / paragraph-rhythm / quantitative-baseline）

## 质量维度定义（所有优化动作的评判标准）

| 维度 | 定义 | 验收标准 |
|------|------|----------|
| **约束程度** | 规则的强制力分级 | 每条规则必须标注：✅ 硬约束（必须/禁止，可客观判定）/ 💡 软约束（建议，附频率证据）；必须有检查清单或量化标准；**主观项（充分/清晰/自然/适当）必须附判定方法或判据词表，否则降级为 💡** |
| **思考深度** | 规则使用的推理结构 | 复杂判断必须有决策树/分支逻辑/推理链（如"若 A 且 B → 做 C"）；**"有分布无选型"（给出占比但无选择条件）是缺陷**：每个分布/句式库必须附选型决策；低频模式必须标注频率与适用条件 |
| **判断边界** | 规则的适用范围与触发条件 | 必须写明：何时该做/不该做、何时询问用户、何时停止、数据缺失时如何降级（[待补]/[待核] 标注）、证据不足时如何标注（⚠ 存疑/需人工复核）；**边界条款必须本地化到每个 section/check 文件**，不能只在 SKILL.md 集中声明 |
| **灵活程度** | 对不同输入的自适应 | 必须覆盖 paper_type（journal/conf/mag）**数值级适配**（conf 摘要/结论/贡献词数、综述段落数；标注"课题组建议，非语料实测——语料均为 journal"）、章节变体、技术场景适配分支；language zh 轴须有最小规则集或明确回退策略 |
| **可溯源性（反幻觉）** | 每条规则的证据链 | 统计声明必须可回溯到语料（给出样本范围与计数）；"语料中不存在 X"类断言必须先 grep 验证；语料无依据的内容必须显式标注来源等级 |
| **交叉一致性** | 四技能间的引用同步 | share 与 writing/polishing/reviewer 使用同一术语、句式、数值口径；**同一规则/边界/深度定义只允许一份权威（其余指针式引用），禁止 3+ 份重复定义导致 drift**；同一事实禁止两个文件矛盾表述 |

### 来源等级标注（每条规则必须归属其一）
1. **语料实测**：可给出语料原文/计数证据，格式如「语料 16/21 篇（76%）使用 we」；
2. **课题组规范**：语料无直接统计但符合 IEEE 惯例或课题组约定；若语料存在反例，必须注明「语料偶见反例，polishing 需纠正」；
3. **外部通用知识**：与语料无关的领域通用知识（如 System Model 章节的 IEEE 写作惯例），必须显式标注「非语料蒸馏」，严禁伪装成语料特征。

## 第一轮蒸馏流程（语料 → 技能初版；v1.0 已执行，流程保留）

### 阶段 0：环境准备与语料加载
- 建立分章节语料库，记录每篇论文标题、字数、段落数、句子数等统计，输出语料概览报告。

### 阶段 1：全局风格特征提取
- 学术正式度、客观性、句式复杂度、词汇偏好、逻辑连接词、时态分布的定量描述，输出全局风格画像。

### 阶段 2：分章节深度结构分析与模板抽取
- 逐章节识别结构模板、句式库、长度约束、逻辑连接方式，输出每章节的 Structural_Template。

### 阶段 3：约束规范抽取
- 提炼硬性约束（必须遵守）与软性建议（最好遵守），每条注明语料来源（至少引用 3 篇论文实例）。

### 阶段 4：生成可执行的 AI SKILL
- 整合为结构化 SKILL 定义（角色设定、全局风格指令、分章节写作规则、交互流程、示例）。

### 阶段 5：迭代验证与优化（可选循环）
- 生成样例与语料对比（BLEU/结构相似度/人工评估），偏差反馈回阶段 2-3 修正。

## 第二轮蒸馏流程（诊断 → 复核 → 优化 → 验证 → 发布；v2.0 已执行，流程保留）

### 阶段 A：现状诊断
- 反幻觉扫描：提取统计声明与规则示例，标注「待核验」；
- 维度缺口扫描：检查缺失维度（约束分级、判断边界、思考深度、灵活度）；
- 查漏补缺扫描：语料高频但技能未覆盖的模式；
- 交叉一致性扫描：同源冲突（同一数据两个数值、同一句式两种判断）。

### 阶段 B：语料实测复核
- 计数规范：统计注明口径（范围/方法/样本量）；「不存在/100%/主流」类断言实际检索；
- 缺失章节处理：System Model 等无语料章节，标注「外部通用知识，非语料蒸馏」，禁止编造语料统计；
- 错误案例核验：polishing/common-errors 每个错误案例须语料实证，找不到的删除。

### 阶段 C：差距优化
- P0 事实性错误 → P1 统计修正 → P2 约束与边界 → P3 查漏补缺与灵活度，按优先级执行并同步所有引用该错误数据的文件。

### 阶段 D：验证
- 抽样回测（3-5 篇真实论文片段跑模板）、交叉一致性检查（关键数值全文检索）、元数据检查。

### 阶段 E：发布
- 审查通过后 dev 副本覆盖发布 skills/，同步 manifest/skills.sh.json/README，git commit。

## 第三轮蒸馏流程（精细打磨；本轮核心）

### 阶段 F：执行质量诊断（在反幻觉已达标的基础上）
对每个文件执行六维**执行质量**扫描（不再重复事实纠错）：

1. **约束可执行性扫描**：找出所有 ✅ 硬约束中**无客观判据**的条目（"充分""清晰""自然""适当""合理"类主观词）→ 标记「需补判定方法」；找出决策树/检查清单中**深度标注冲突**（light/moderate/deep 与权威边界矛盾）；
2. **思考深度扫描**：找出所有**「有分布无选型」**结构（句式库/模式表给出占比但无选择条件）→ 标记「需补选型决策」；找出缺分支的决策树（"素材不足怎么办"“数据缺失怎么办”）；
3. **判断边界扫描**：检查边界条款是否**本地化**到每个 section/check 文件（不能只在 SKILL.md 集中）；找出仍直接写"补充/添加"未加授权提示的分支；找出未定义 [待补]/[待核]/⚠ 标注规范的位置；
4. **灵活度扫描**：确认 conf/mag 是否有**数值级**适配分支（非"篇幅压缩"四字）；zh 轴是否有最小规则；
5. **查漏补缺扫描**：对照语料找仍可补的高频错误案例（拼写/搭配）与高频句式/术语；
6. **交叉一致性扫描（去重）**：找**重复定义**（同一规则 3+ 份权威声明）与**口径冲突**（数值/占比/排序矛盾）。

**输出**：`distillation-diagnosis-v130.md`（按技能 × 文件，每条：位置 | 问题类型 | 描述 | 建议 | 优先级 P0-P3）。

### 阶段 G：精细优化（按优先级）
- **P0 硬性交叉冲突**：数值/占比/归属矛盾（如连接词表混口径、被动语态区间冲突、示例归属矛盾）立即修正并全链路同步；
- **P1 思考深度与可执行性**：为每个「有分布无选型」决策点补选型树（1-3 行判据）；为每个主观 ✅ 检查项补判定方法/判据词表或降级 💡（参照 paragraph-rhythm §4.5 的计数法标杆）；
- **P2 判断边界与查漏补缺**：边界条款本地化到全部 section/check；common-errors 补语料实证错误（拼写类/搭配类）；share 补高频术语/句式；
- **P3 灵活度与版本同步**：conf/mag 数值适配表（标注"课题组建议，非语料实测"）；版本号全局 1.3.0。

**每文件修改后自检**：
- [ ] 所有 ✅ 硬约束可客观判定（无主观词裸奔）
- [ ] 所有分布/句式库附选型决策
- [ ] 判断边界本地化（含 [待补]/[待核]/⚠ 规范）
- [ ] 与共享层数值、术语、句式无冲突、无重复权威
- [ ] 来源等级标注完整

### 阶段 H：验证（发布门禁）
1. **抽样回测**：从语料抽取 3-5 篇真实论文片段，用优化后的模板/清单跑一遍，确认可判定、无全数误判；
2. **交叉一致性检查**：全文检索关键数值与术语（词数/we 密度/连接词排序/TABLE 编号/时态规则/被动语态区间），确认四技能完全一致；
3. **深度标注核对**：polishing 所有决策树深度标注与 workflow 唯一权威边界一致；
4. **元数据检查**：版本号 1.3.0、引用路径、manifest 与文件一致。

**输出**：`验证报告.md`，含回测结果与一致性检查表。

### 阶段 I：发布
1. 质量审查（review 工具）通过前改动仅存 dev 副本；
2. 审查通过后 dev 副本整体覆盖发布 `skills/`（git 保留 v1.2.0）；
3. 同步 `skills.sh.json`、`README.md` 版本/描述；
4. git commit（信息含版本号与变更摘要）；
5. 清理 dev 下四个技能副本（保留语料库、诊断报告、promot.md）。
